# V1.5 — Ads + Android Shipping: Plan (Slice 0)

Status: **Slice 0, planning only.**
- Branch: `feature/v1.5-ads-android`.
- Slice 0 installed no SDK or plugin, added no ad code and built no APK or AAB.

V1.5 has one purpose: turn the released v1.2.0 web product into a monetized app that can ship on Android, without changing
how it works out anyone's colours. V2.0 generative AI is a separate track ([V2_AI_LAB_BOUNDARY.md](V2_AI_LAB_BOUNDARY.md)).

- Capacitor Android integration;

- Quiz, Result and My Palette;
- the Manual and Photo Color Checker;
- Daily Lucky Color;
- Learn.

Not tuned in V1.5:
- the classifier, subtype targets and palettes;
- the Photo colour algorithm;
- Daily's recommendation logic;
- Learn's content architecture.

Known Photo colour differences are an accepted V1.x limitation (§38). The weaker Daily graphic is visual debt, not a mandate

## 4. V2.0 boundary

V1.5 excludes all of the following:
- generative AI;
- AI colour estimation and AI photo correction;
- vision-model garment understanding;
- AI outfit generation and an AI stylist or chat;
- paid inference APIs and an AI backend;
- AI credits or subscriptions.

No V1.5 structure is shaped around V2. The only thing both will share is the existing local-first app shell.

## 6. Web app shell and integration points

- **Views:** state-based, no router. `App.tsx` holds `view: 'home' | 'presentation' | 'quiz' | 'result' | 'palette' | 'checker' | 'daily' | 'learn'`.
  - Each view renders its own `<main>` inside `.app-shell`, with `AppHeader` above.
  - Learn has its own internal pages (home, topic, type) inside `LearnView`.
- **Global navigation:** `BottomNav` in `App.tsx`.
  - It is `position: fixed`, a floating pill 18 px from the bottom, or 10 px on phones.
  - It is hidden on `quiz` and `presentation`, and before a result exists.
  - V1.4 Slice 5 added a `ResizeObserver` that publishes `--bottom-nav-height` on `.app-shell`, which reserves bottom
    padding. Below 250 CSS px the nav becomes static.
- **Shared container:** every screen is a direct child of `.app-shell`, which owns the page padding. This is the one place
  where space for an ad can be reserved.
- **Safe areas:** the web CSS uses no `env(safe-area-inset-*)`, and `index.html` has no `viewport-fit=cover`.
  - In Capacitor 8, the built-in `SystemBars` plugin checks for `viewport-fit=cover`.
  - **Without it, SystemBars pads the decor view by the system bars**, so the WebView sits between the status bar and the
    navigation/gesture bar.
  - The injected `--safe-area-inset-*` variables are then 0 (read from `SystemBars.java` in `@capacitor/android` 8.5.2).
  - So the current app needs no safe-area CSS on Android (§25).
- **Existing ad seam (important):** `src/services/ads.ts` already defines `AdService`, with `showInterstitial` and
  `showRewarded`, plus the placements `'palette_open' | 'photo_check_bonus'` and a `NoOpAdService`.
  - `App.tsx` `changeView` already awaits `adService.showInterstitial('palette_open')` on **Result → Palette**.
  - `photo_check_bonus` is unused. The V1.2 plan §19 forbade gating Photo on a reward.
- **Where ads belong:** at `App`, which knows the current `view`. Feature components never need to know about ads (§19).

## 7. Existing guards that V1.5 must change on purpose

`src/releaseCandidate.test.ts` (V1.2 Slice 8) currently enforces:
1. only the three `@capacitor/*` packages, **no plugin**;
2. **no app source imports `@capacitor/`**;

4. the photo input is `<input type="file" accept="image/*">` with no `capture`.

- keep "no photo code imports Capacitor" as a separate, stronger guard.

Guard 3 changes only as §30 describes. Guard 4 stays.

## 8. Ads provider research

Sources were read on 2026-09-25 (§42).

| Option | Status | Capacitor 8 | Notes |
|---|---|---|---|
| **`@capacitor-community/admob` 8.1.0** | "Actively Maintained", MIT; the plugin the Capacitor docs' ads guide recommends | v8 targets Capacitor 8 (`@capacitor/core ^8.0.0`), Android API 24+ | Bundles Google Mobile Ads SDK 25.4.x (Android) and UMP 4.0.0. Supports banner, interstitial, rewarded, rewarded interstitial and app-open ads, plus the consent API. |
| `@capawesome-team/capacitor-admob` | New (announced 2026-09-07), Capacitor 8+ | yes | **Paid (Capawesome Insiders).** Has "overlay / resize / inline frame" banner modes, which is technically attractive. Rejected: it's a paid dependency, and it's new. |
| Writing our own native plugin | n/a | n/a | Rejected: more native code to maintain, for no gain in V1.5. |

**Recommended:** `@capacitor-community/admob@8`, pinned to an exact version like the rest of `package.json`.

Key facts about the community plugin:
- **Initialization:**
  - `AdMob.initialize({ initializeForTesting, testingDevices, tagForChildDirectedTreatment, tagForUnderAgeOfConsent, maxAdContentRating })`.
  - Google says to handle consent and request flags **before** initialising, because the SDK may preload ads.
- **Consent:** `requestConsentInfo()`, then `showConsentForm()` if the status is `REQUIRED`, then check `canRequestAds`. Also
  `showPrivacyOptionsForm()` and `resetConsentInfo()`.
- **Banners:**
  - `showBanner({ adId, adSize: 'ADAPTIVE_BANNER', position: 'TOP_CENTER' | 'CENTER' | 'BOTTOM_CENTER', margin, isTesting, npa })`, plus `hideBanner`, `resumeBanner` and `removeBanner`.
  - Events include `bannerAdSizeChanged`, loaded and failed.
  - The README says the banner "sits above the WebView and can cover HTML". **The app must reserve space itself.**
- **Test support:** `isTesting` for each request, test devices, and Google's demo ad unit IDs (§21).
- **Native configuration:**
  - `<meta-data android:name="com.google.android.gms.ads.APPLICATION_ID" android:value="@string/admob_app_id"/>` in the
    manifest. **Without it the SDK crashes on start ("Missing application ID").**
  - Optionally `playServicesAdsVersion` and `userMessagingPlatformVersion` in `variables.gradle`.
- **Web behaviour of the plugin:** its web implementation only logs, and returns **fake consent data (`status: REQUIRED`)**.
  It must therefore never be called on the web. It sits behind the platform gate (§20).
- **Google SDK lifecycle:**
  - Google calls the "legacy" Mobile Ads SDK **maintenance mode** and recommends the GMA Next-Gen SDK.
  - Android v25.x is supported until **deprecation 2027-06-30 and sunset 2028-06-30**.
  - The plugin's next major release is expected to move to Next-Gen.
  - This is acceptable for V1.5, but it is a **known maintenance item**: plan a plugin major upgrade before mid-2027.
- **Platform requirements:** min SDK 24 and compile SDK ≥ 35. The project has 24 and 36. ✔

**Nothing here is a STOP condition:**
- the plugin is compatible with Capacitor 8.5.2, maintained and MIT-licensed;
- the app shell already has a seam for it, so no architecture rewrite is needed.

## 9. Web vs native ads

**Recommendation: A, native ads inside the Android app only. The web app stays ad-free in V1.5.**

Reasons:
- **Different stacks.** AdMob serves apps. Web ads would need AdSense or Ad Manager for web: another account, another
  consent setup (a web CMP/TCF banner), external scripts in a page that currently makes **zero** external requests, and
  new Vercel-side privacy work. Nothing is shared with the native implementation.
- **The web is the free, clean front door.** It is also where the product was just released and smoke-tested.
- **Monetizing the web** can be a later, separate decision, with its own plan.

## 11. Protected experiences (hard rules)

No ad of any format may appear or be triggered:
- while answering Quiz questions, including the presentation choice before the quiz;
- between completing the quiz and the first Result being shown, or over the Result screen;
- while choosing or uploading a photo, tapping a garment or sample point, or while the Color Checker is computing or
  showing its immediate result (Manual or Photo);
- over the retake dialog or the image viewer dialogs.

Implementation rule: the ad boundary is told the current *screen* by the shell. Protected screens map to "no slot", so they
never show a banner, and no interstitial trigger exists.

| **Learn (home, topic, type guide)** | Reading content with clear page tops | Medium | Low | **Banner allowed** |

| **After the result** (a later visit to Result) | The Result is the returning user's home screen | High | High: it is the product's core answer | **Avoid in V1.5** |

Ads must look clearly different from the app's advice:
- the plugin's native banner is visibly an ad;
- the shell adds a plain, non-clickable separator band;
- no ad is ever styled like, or placed inside, a palette or outfit card.

## 13. Recommended V1.5 ad strategy (smallest viable)

1. **Android only.** The web stays ad-free.
2. **One anchored adaptive banner**, **at the top**:
   - it sits under the status bar, above the app header, with a non-clickable separator;
   - it appears **only on Daily and Learn** (Learn's home, topics and type guides);
   - Palette is added only if the PO opts in after device QA.
3. **No interstitial, rewarded or app-open ads at launch.**
4. **Consent is gathered through Google's UMP** (§16). The form is shown only when UMP says it is needed, and **not before
   or during the Quiz**.
5. **Ads fail open everywhere** (§22).

Why the top and not the bottom: Google warns specifically against banners next to "a custom app menu bar", and says to keep
"sufficient separation … from navigational elements such as menu bars". The bottom nav is the app's most-tapped control, in
the thumb zone. A bottom banner would sit directly against it. At the top, the banner borders only the header's language
and presentation switchers, which are tapped rarely and sit further from the thumb. Either position needs a separator.
**PO decision D3** confirms the position.

## 15. Frequency proposal

- **Banner:**
  - one banner instance for the whole session;
  - shown on entering an ALLOW screen, hidden (not destroyed) on leaving, and resumed on return;
  - no new ad request on each navigation;
  - AdMob's console refresh at **≥ 60 s**, or off;
  - no banner until consent is resolved and `canRequestAds` is true.
- **App start:** no ad at start.
  - The consent-info update runs silently.
  - Any form appears on the first visit to an ALLOW screen, never over Welcome, the Quiz or the Result.
- **Repeated Checker use:** never an ad (AVOID).
- **Repeated Daily visits:** the same resumed banner. No extra formats, no "come back for more" loop, and no reward for
  visiting.
- **If an interstitial is ever approved (post-launch, PO opt-in):**
  - at most **1 per session** and at most 1 per 10 minutes;
  - never in the first session after install, and never within 2 minutes of launch;
  - only when **leaving** Daily or Learn for another screen;
  - never into or out of Quiz, Result or Checker;
  - never back to back with another ad;
  - always preloaded, skipped if not ready, and never awaited in a way that blocks navigation.

## 16. Consent, privacy and policy

From official documentation; no legal claims are made here.

- **Google's UMP SDK** (bundled by the plugin) is Google's consent tool.
  - Google's pattern is to call `requestConsentInfoUpdate` **on every launch**, show a form only when required, and request
    ads only while `canRequestAds()` is true.
  - Google says to handle consent **before** initialising the Mobile Ads SDK, which can preload ads.
  - Plan: silent consent-info update at launch → form, only if required, at the first ALLOW screen → `initialize` → banner.
  - Until then there is no ad, and the app is unaffected.
- **EEA, UK and Switzerland:**
  - Google's EU User Consent Policy applies, and Google's own consent message (a certified CMP) covers it.
  - The GDPR message and any US state regulation messages are **configured in the AdMob console (Privacy & messaging)**.
    This is an account task for the PO.
- **Privacy options entry point:** when UMP reports the privacy options as *required*, the app must offer a way to reopen
  them (`showPrivacyOptionsForm`).
  - The app has no settings screen.
  - Proposal: a small "Ad privacy choices" text link in the Android app only, placed in the header area or at the foot of
    Learn home. **PO decision D8.**
- **Personalized vs non-personalized:** UMP and the consent string decide this. Do not pass `npa` ourselves unless the PO
  chooses non-personalized ads for everyone (**D9**).
- **Children:**
  - If the Play target audience includes children, Families policy requires ads from self-certified SDKs, child-directed
    tags, and **no app-open ads**.
  - Recommendation: target 13+ or 18+, not children. **D7.**
  - The initialization flags (`tagForChildDirectedTreatment`, `tagForUnderAgeOfConsent`, `maxAdContentRating`) follow that
    decision; a conservative content rating (e.g. `T`) is suggested.
- **ATT:** iOS only. Not relevant unless iOS is added.
- **Manifest metadata:**
  - the AdMob `APPLICATION_ID` is **required** (§8);
  - the Mobile Ads SDK merges its own permissions (§30).
- **Test vs production IDs:** §21.
- **Privacy policy:** Play requires one before the app content forms can be completed. It must now cover the ad SDK's
  collection (below) and state what the app itself does *not* send (§17). The text and its hosting are **D10**.
- **Data safety:**
  - Google documents that Mobile Ads SDK 25.x collects the IP address (approximate location), product interactions,
    diagnostics, and device or other identifiers (advertising ID, app set ID).
  - Purposes: advertising, analytics and fraud prevention. Data is encrypted in transit.
  - The Data safety form must declare these, and "Contains ads" must be declared in App content.
  - The app itself collects nothing else and has no account.
- **app-ads.txt:**
  - AdMob strongly recommends it at the root of the *developer website* listed on Play.
  - Hosting it on the Vercel site would be a web change on `main`. **D11.**

## 17. User data boundary (hard V1.5 rule)

The ad SDK may collect what it collects under its documented operation and the user's consent. **The app itself never adds
Personal Color Pocket data to an ad request.** Specifically, it never passes:
- quiz answers, subtype, season, or result confidence;
- palette or selected colours, HEX values, or colour names;
- the Photo Checker image, sampled pixels, or derived colours or verdicts;
- Daily goals, lucky colours or outfit data;
- language or presentation preference used as targeting (the SDK's own device locale is outside our control);
- Learn topics viewed.

Enforcement:
- The ad boundary's public API takes **only a slot/screen id from a closed union**.
- It passes **no** `keywords`, `contentUrl`, `neighboringContentUrls` or custom targeting. The plugin's options must be
  built from constants.
- A source guard test (in the ads slice) forbids imports from `domain/`, `photoChecker/`, `dailyLuckyColor/`, `learn/`,
  `services/persistence` and `services/photoImage*` inside the ads module.
- It also forbids targeting keys in the module source.

## 18. Photo privacy

- **The image never reaches the ad layer.**
  - The photo lives in the Photo panel's state and a canvas.
  - The ad module can't import photo code (guard above), and its API can't carry data.
- **The native banner is a separate Android view** laid over the WebView. The Mobile Ads SDK does not read WebView content
  unless the app calls its WebView API for Ads (`registerWebView`), which **the app will never call** (to be guarded).
- **No photo upload, and no image- or sampled-colour-derived targeting.**
- **The Photo Checker is AVOID** (§14), so no ad is even on screen while a photo is open.
- **The on-screen promise "Your photo stays on this device" remains true** and needs no change.
- The Welcome line "No photos. No account. Your answers stay on this device." also remains literally true. Whether the
  Android build needs an extra line about ads is part of **D10**.

## 19. Ad abstraction (design only, no code in Slice 0)

Proposed as a replacement for the existing `src/services/ads.ts`, keeping its file location:

```ts
// src/services/ads.ts (or ads/index.ts): the only module that knows an ad SDK exists
export type AdScreen = 'home' | 'presentation' | 'quiz' | 'result' | 'palette' | 'checker' | 'daily' | 'learn'
export type AdSlot = 'top-banner'
export interface AdsService {
  start(): Promise<void>                       // consent-info update and init. Never throws; resolves even offline.
  setScreen(screen: AdScreen): void            // the shell says where the user is; policy decides show/hide
  onLayout(cb: (inset: AdInset) => void): () => void  // the banner's reserved height (0 when none)
  showPrivacyOptions?(): Promise<void>         // only when consent says an entry point is required
}
export function slotFor(screen: AdScreen): AdSlot | null   // the §14 matrix as pure data, unit-tested
```

- **`NoOpAdsService`:** web and tests. It does nothing and always reports an inset of 0.
- **`AdMobAdsService`:** Android only, loaded by `import()` behind the platform gate, so the plugin stays out of the web's
  main chunk.
- **The shell (`App`)** calls `setScreen(view)` in an effect and writes `--ad-top-inset` on `.app-shell`, as `BottomNav`
  already does for `--bottom-nav-height`.
- **Feature components** (Quiz, Result, Checker, Daily, Learn) are **untouched** and never import the ads module.
- **Retired:** `showInterstitial`, `showRewarded`, `'palette_open'`, `'photo_check_bonus'`, and the `await` in `changeView`.
  Navigation must never wait on an ad.

## 20. Platform detection

- **Mechanism:** use `Capacitor.getPlatform() === 'android'` (with `Capacitor.isNativePlatform()`) from `@capacitor/core`, the
  official API. No user-agent sniffing.
  - On the web it returns `'web'`.
  - Inside the Android WebView the native bridge makes it `'android'`.
- **Where it is used:** only inside the ads boundary. The gate runs before the dynamic `import()` of the plugin adapter.
  - **Web:** `NoOpAdsService`. The plugin is never loaded or called, so its fake-consent web stub is never reached.
  - **Android:** `AdMobAdsService`.
- **Cost to the web bundle:** it gains `@capacitor/core`'s small runtime. The plugin chunk is emitted but never fetched on
  the web. Measure it in the ads slice against the V1.4 budget practice (investigate if it grows by more than 5 kB gzip).

## 21. Test vs production ad configuration

- **Default is test.** Google's demo IDs (Android):
  - adaptive banner `ca-app-pub-3940256099942544/9214589741`;
  - interstitial `…/1033173712` (for reference only).
- **Google warns** that clicking live ads during development can get the account flagged for invalid activity.
- **App ID** (manifest):
  - from a Gradle `manifestPlaceholders` / `resValue`, fed by a **git-ignored** `android/ads.properties` or an
    environment variable;
  - falls back to Google's sample app ID for debug builds.
- **Ad unit IDs:**
  - baked into the web build through Vite env: `VITE_ADS_MODE=test|live`, `VITE_ADMOB_BANNER_ID`;
  - real values live only in a **git-ignored** `.env.production.local`. `*.local` is already in `.gitignore`.
- **Hard separation rules:**
  - `live` needs an explicit `VITE_ADS_MODE=live` **and** a real ID. Otherwise the service uses the demo ID **and**
    `isTesting: true`.
  - `npm run build` is always Vite "production" mode, so the mode alone must never select live IDs.
  - The live release build **fails the build** (not the app) if live mode is requested without IDs.
  - Automated tests and debug APKs always run in test mode, and test devices are registered for physical QA.
- **Are the IDs secret?**
  - Ad unit and app IDs are not credentials. They ship inside every APK.
  - The repo is **public**, so real IDs stay out of git anyway, to limit misuse (invalid traffic against our units).
  - No production ID will be committed.

## 22. Failure behaviour: fail open

In every one of these cases, **the app renders exactly as v1.2.0 and the reserved inset stays 0**:
- the SDK is missing;
- the plugin is unavailable (web);
- the device is offline;
- consent is unresolved or denied (`canRequestAds` false);
- the load fails, or there is no fill.

Rules:
- `start()` never rejects, and has a timeout.
- Navigation and features never await the ad service.
- No placeholder "Ad" box or blank band is shown before or instead of a loaded ad.
- A failed load is not retried in a loop; at most one retry on the next ALLOW screen entry.

## 23. Offline

- The core features are local and stay usable offline, exactly as now.
- Ads simply don't appear offline, and nothing waits for the network.
- The consent-info update fails quietly offline.
- The app's own assets are in the APK (`assets/public`), so the native app has an even better offline start than the web.

## 24. Layout reservation

The native banner **overlays** the WebView, so the page must make room for it:
- **Reserve only after the ad loads.**
  - `bannerAdSizeChanged` / loaded gives the height, and the shell sets `--ad-top-inset` to the height plus the separator.
  - On failure it stays 0. This avoids an empty band offline or with no fill, at the cost of one layout shift when the ad
    arrives.
  - Google recommends a fixed space so content doesn't jump. The trade-off is recorded here, and a device check decides it.
- **Separator:** a fixed, non-clickable web band (hairline and background) at the banner's lower edge, at least 8 px.
- **What moves with the inset:**
  - `.app-shell` `padding-top`;
  - the existing sticky offsets (`.daily-outfit` `top: 24px`, `.selected-color` `top: 14px`) become
    `calc(var(--ad-top-inset, 0px) + …)`;
  - `scroll-padding-top`, so Learn's focus-to-`h1` and keyboard focus aren't hidden under the banner.
- **Protected:** the bottom nav is untouched by a top banner. Photo controls and quiz answers are on AVOID screens, so they
  are never near a banner.
- At 200% text and zoom (V1.4 Slice 5), the nav may become static below 250 CSS px. A top banner doesn't interact with that.

## 25. Android safe areas

- **Status bar and gesture/navigation bar:** Capacitor 8's `SystemBars` pads the decor view unless the page opts into
  `viewport-fit=cover`.
  - **Keep it that way.** Do not add `viewport-fit=cover`, so the WebView never draws under the system bars, and the fixed
    bottom nav needs no inset.
  - This is the case for `targetSdk 36`, where edge-to-edge is enforced; the Capacitor 8 template handles it.
- **The banner's attachment point** relative to that padding (whether `TOP_CENTER` lands under the status bar) must be
  **verified on a device in the ads slice**.
  - If it overlaps, use the plugin's `margin` or `--safe-area-inset-*`, never fixed pixel values.
- **Keyboard:** Manual Checker's HEX field is an AVOID screen, so the keyboard and banner never meet.

## 26. Orientation

- **Not locked:** there is no `android:screenOrientation`, and `configChanges` includes orientation, so rotating
  re-lays-out the WebView without restarting.
- **Landscape:**
  - the web layout is responsive (320–1280 px was QA'd in V1.4);
  - a phone in landscape shows the desktop-ish layout at a short height;
  - it has not been checked on a device.
- **Android 16 / targetSdk 36:** on screens with **smallest width ≥ 600 dp** (tablets, foldables), orientation and
  resizability restrictions **are ignored**. The opt-out goes away at API 37. So landscape must work regardless, and a
  portrait lock could only ever apply to phones.
- **Recommendation:** no lock; landscape is covered in device QA.
  - An adaptive banner must be re-requested at the new width after rotation. This is handled in the ads slice.
  - **PO decision D6:** accept rotation, or lock phones to portrait.

## 27. Android back button

- **Current behaviour:**
  - Capacitor's back handling lives in `@capacitor/app`, which is not installed.
  - `BridgeActivity` doesn't override back (no `onBackPressed` or `OnBackPressedCallback` in `@capacitor/android` 8.5.2).
  - So Android Back does the Activity default: it **leaves the app from any screen**, including mid-Quiz and inside a Learn
    page.
  - The app is state-based with no history entries, so WebView history wouldn't help either.
- **Recommendation: include a small back-handling step in V1.5.**
  - It needs `@capacitor/app`, a second official plugin, allowed by the narrowed guard (§7).
  - One shell-level handler, Android only:
    - a dialog or viewer is open → close it;
    - Learn topic or type → Learn home;
    - Quiz step > 0 → previous step;
    - any other non-root screen → the root (Result if a profile exists, otherwise Welcome);
    - at the root → `App.minimizeApp()` (don't kill the app).
  - The web's browser Back stays as documented in V1.4 (unchanged).
  - **PO decision D5.**

## 28. Android photo picker

- `PhotoCheckerPanel.tsx` uses `<input type="file" accept="image/*">` with no `capture` (test-guarded).
- V1.2 Slice 8 §10 read the source of Capacitor 8.5.2's `BridgeWebChromeClient.onShowFileChooser`:
  - with no capture flag it opens the **system picker**, with **no runtime permission**;
  - it returns a `content://` URI with a temporary read grant, delivered to the page as an ordinary `File`.
- **Recommendation:** the standard file input is enough. **No Camera or Photo plugin.**
- Still to confirm on a device (build needed): the picker, large images, and the "Your photo stays on this device" path
  (QA §35).

## 29. Permissions

- **Now:** `INTERNET` only.
- **Expected final set:**
  - `INTERNET`;
  - the Mobile Ads SDK's **merged** permissions: `ACCESS_NETWORK_STATE` and `com.google.android.gms.permission.AD_ID`
    (normal, install-time; the SDK adds them);

## 33. Signing and release builds

- **Now:** there is no `signingConfigs` block; the `release` build type is unsigned (`minifyEnabled false`), with no
  keystore anywhere. Keystore files are not git-ignored yet (the template leaves `*.jks` / `*.keystore` commented out), so
  the store slice adds those rules **before** any keystore exists.
- **Plan:**
  1. **Debug APK** (`gradlew assembleDebug`) for device QA. It is signed with the debug key.
  2. **Release AAB** (`gradlew bundleRelease`) for Play, which uses AABs and **Play App Signing** for new apps.
  3. **Upload key:**
     - a keystore the PO creates and keeps **outside the repo**, backed up;
     - Gradle reads its path and passwords from a git-ignored `android/keystore.properties` or environment variables;
     - Google holds the app signing key.
- **Versions:** `versionName` and `versionCode` must follow the product version (1.2.x → e.g. versionCode derived from
  semver) instead of the template's 1 / "1.0". This is decided in the store slice.
- **PO and manual setup:**
  - install the SDK (licence acceptance);
  - create the upload keystore;
  - Play Console developer account and app creation;
  - accept Play App Signing.

## 41. Known limitations and risks

- **SDK:** no Android SDK on this PC. Nothing native has ever been built or run, so every native claim here is from source
  or documentation until Slice 1.
- **Google's SDK is in maintenance mode.** The legacy Mobile Ads SDK is deprecated in 2027-06 and sunset in 2028-06, so
  the plugin will need a major upgrade before then.
- **Banner attachment:** where the plugin's banner lands relative to Capacitor 8's decor-view padding is unverified until a
  device run.
- **Reserve on load:** reserving space only after an ad loads causes one layout shift. This is a deliberate trade-off for
  fail-open (§24).
- **Android Back** currently leaves the app from any screen (§27). The web keeps its V1.4 back behaviour.
- **Placeholders:** the icons and splash are placeholders; versionName/Code are template values.
- **Earlier V1.0–V1.3 items** carry forward unchanged: contrast failures, 32 px switchers, and some 200% zoom widths.
- **A new personal Play account** needs 12 testers for 14 days before production. That is calendar time outside
  engineering control.
